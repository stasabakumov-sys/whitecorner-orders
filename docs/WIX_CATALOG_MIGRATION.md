# Перенос каталога Wix в White Corner

Дата исследования: 10 сентября 2026. Это план, а не отчёт о выполненном импорте.

## Цель и текущее состояние

Цель владельца — собственный backend с необходимыми функциями Wix и собственный frontend, которые затем соединяются. Перенос каталога — первый самостоятельный этап. Экспорт товаров переносит данные; checkout, платежи, возвраты, документы, автоматизации и другие бизнес-процессы необходимо реализовать и проверить отдельно.

Read-only проверка production Supabase на эту дату показала:

| Объект | Количество |
|---|---:|
| Товары `wc_shipping_products` | 40 |
| Из них с `wix_product_id` | 30 |
| Без связи с Wix | 10 |
| Активные товары Hub | 40 |
| Строки упаковки `wc_shipping_packages` | 13 |
| Сохранённые профили упаковки | 13 |
| Профили себестоимости | 1 |
| Чертежи товаров | 4 |
| Чертежи коробок | 1 |

На скриншоте пользователя Wix показывает **177 товаров**. Это ориентир интерфейса, а не подтверждённое число объектов API. Нельзя заранее считать, что нужно добавить 177 − 40 товаров: среди локальных записей могут быть исторические, несвязанные или уже переименованные товары.

Рабочая база при исследовании не изменялась. Версия каталога конкретного сайта и фактически выданные права Products API ещё не проверены.

## Что уже существует в Hub

`wc_shipping_products` — действующий операционный реестр, а не полный каталог Wix. Он содержит внутренний UUID, внешний Wix ID, название, тип, активность и локальные поля. Регистрация из заказов уже сопоставляет Wix ID, затем несвязанное название и создаёт недостающую запись (`wc_catalog_register`, migration `20260908000400_catalog_product_costing.sql`). Отдельного полного импорта Wix Stores Products сейчас нет.

К внутренним ID привязаны упаковки, правила, профили и чертежи. Некоторые связи имеют `ON DELETE CASCADE`, поэтому удаление реестра с последующим созданием заново недопустимо. `short_name`, `manual_sizes`, notes и операционная активность — локальные данные. Их нельзя заменять импортом целой строки.

Часть представления Products собирается из позиций заказов и шаблонов упаковки. Записи с синтетическим UI ID `saved:...` не являются самостоятельными строками товаров: при сверке их нужно связать с реальным UUID. Исторические названия, варианты и цены в заказах сохраняются независимо от обновления каталога.

## Как читать каталог Wix

Сначала определить версию через `GET https://www.wixapis.com/stores/v3/provision/version`. Сайт использует Catalog V1 либо V3; выбирать API по возрасту сайта или виду dashboard нельзя. У метода проверки версии указано отдельное разрешение `Read v3 catalog (PII)`; наличие текущего ключа для Orders не доказывает доступ к каталогу. [Get Catalog Version](https://dev.wix.com/docs/api-reference/business-solutions/stores/catalog-versioning/get-catalog-version).

| Версия | Получение товаров | Существенное отличие |
|---|---|---|
| V1 | `POST /stores-reader/v1/products/query`, до 100 на запрос | Запрашивать варианты явно через `includeVariants`; отдельно учитывать скрытые товары |
| V3 | `POST /stores/v3/products/query`, до 100, cursor pagination | Список не возвращает варианты; получать детали/варианты дополнительно |

Источники: [V1 Query Products](https://dev.wix.com/docs/api-reference/business-solutions/stores/catalog-v1/catalog/query-products), [V3 Query Products](https://dev.wix.com/docs/api-reference/business-solutions/stores/catalog-v3/products-v3/query-products).

В V1 `includeHiddenProducts` требует Manage Products, а `includeVariants` ограничен 1000 вариантами на товар. Не считать скрытый каталог пустым при недостаточных правах. Если сайт V1 потребует более широкого разрешения для чтения скрытых товаров, отдельно объяснить владельцу причину; код импортера всё равно должен выполнять только чтение. [Параметры V1](https://dev.wix.com/docs/api-reference/api-reference/wix-stores/catalog/query-products).

В V3 нужны Read products in v3 catalog и дополнительное Product v3 read admin для невидимых товаров. Для каждого продукта получать необходимые подробные поля и варианты через Get Product либо отдельный variants API. В Read-Only Variants устаревший `id` не гарантирует уникальность: ключ варианта включает `productId` и `variantId`. [Get Product](https://dev.wix.com/docs/api-reference/business-solutions/stores/catalog-v3/products-v3/get-product), [Query Variants](https://dev.wix.com/docs/api-reference/business-solutions/stores/catalog-v3/read-only-variants-v3/query-variants).

Остатки — отдельная сущность. V3 Inventory API требует Read inventory in v3 catalog и поддерживает страницы до 1000. Нужно сохранять tracking, доступность, количество и связь с локацией, а не превращать «in stock» в выдуманное количество. [Query Inventory Items](https://dev.wix.com/docs/api-reference/business-solutions/stores/catalog-v3/inventory-items-v3/query-inventory-items).

CSV полезен как дополнительная резервная копия и для ручной сверки. Основной импорт предлагается строить через API со стабильными ID и явной проверкой полноты. CSV нельзя считать экспортом всего backend. [Wix: exporting and importing products](https://support.wix.com/en/article/wix-stores-exporting-and-importing-your-products).

## Предлагаемая модель и владение данными

Сохранить `wc_shipping_products.id` как существующую внутреннюю идентичность. Расширять каталог связанными сущностями и миграциями, не создавать второй несвязанный список Products. Конкретные имена новых таблиц определить после изучения реального ответа API.

Необходимые группы данных:

- Карточка: внешний ID и сайт-источник, название, описание, slug/URL, видимость, тип, бренд, категории, SEO, дополнительные информационные разделы.
- Варианты: ID, опции и значения, SKU, цена и скидки, вес, изображения, доступность; персонализация и customizations отдельно от вариантов, где этого требует Wix.
- Inventory: отдельные записи доступности/количества по варианту и локации.
- Media: порядок, назначение, исходные идентификаторы и URL. Для независимости позже переносить доступные принадлежащие White Corner файлы в собственное хранилище с проверкой ссылок и количества.
- Источник и импорт: provider/site/external ID, версия каталога, revision/update time при наличии, время чтения, исходный snapshot и статус полноты деталей.

Нормализованные поля нужны собственному приложению; исходный snapshot помогает диагностике и повторной обработке. Учесть уже обнаруженные при импорте Orders ограничения JSONB для NUL/некорректных суррогатов: безопасное нормализованное представление и, при необходимости, точный сериализованный источник в text. Не логировать полные payloads и не помещать реальные данные в fixtures.

| Поля | Источник на первом этапе |
|---|---|
| Коммерческая карточка, варианты, продажные цены, видимость, inventory | Wix, только чтение |
| Упаковки, чертежи, материалы, себестоимость, short name, manual sizes, notes | Hub |
| Исторические позиции заказов и расчёты | Сохранённый снимок соответствующей операции |
| Будущие собственные изменения каталога | После отдельного решения о переключении владения |

Цвет Raw/White/другой сохраняется в каталоге: он может менять цену, SKU, остатки и работу производства. Только подбор упаковки игнорирует цвет по принятому правилу. Size и Foldable продолжают участвовать в подборе. Размер товара не заменяет размеры коробки, а вес товара — вес упакованного отправления.

## Сверка без потери существующих товаров

1. Загрузить источник в staging и сформировать отчёт: связанные, новые, кандидаты на связь, конфликты, отсутствующие в текущем ответе.
2. Для 30 связанных строк сопоставлять точный Wix ID и сохранять внутренний UUID. Изменённое название не создаёт новый товар.
3. Для 10 несвязанных строк показать кандидатов. Название, SKU и slug — дополнительные признаки, а не универсальные ключи. Неоднозначное соответствие требует ручного решения.
4. Учитывать сохранённые профили без строки реестра, связывая их с каноническим товаром, без потери signatures и drawing links.
5. Создавать подтверждённо новые товары и обновлять только поля Wix. Согласовать транзакционную защиту с существующей регистрацией товаров из заказов, чтобы параллельный sync не создавал дубликаты.
6. Отсутствующий товар не удалять автоматически. Сначала проверить полноту загрузки, скрытые товары и права; историческую запись сохранять даже после удаления источника.

Первое применение выполнять после просмотра конкретного отчёта сверки. До этого подготовить механизм импорта, проверки и отчёт, а не просить одобрение абстрактного переноса.

## Надёжность загрузки и дальнейшая синхронизация

Импорт должен работать серверными ограниченными порциями с постоянным job/checkpoint, а не зависеть от открытой вкладки. Продвигать checkpoint после успешной записи страницы. Повтор той же страницы безопасен благодаря внешним ключам и upsert. Ограниченные retries для 429/временных 5xx; ошибки доступа и валидации сохранять как понятное состояние задачи.

Отдельно показывать: прочитано товаров, сохранено карточек, завершено деталей/вариантов, конфликты и ошибки. Счётчик строк в UI не подтверждает полноту переноса. После завершения сверять уникальные ID источника и БД, страницы, варианты, обязательные поля и связи. Отсутствующее поле не заменять нулём или пустым массивом без понимания контракта.

Сначала достаточно полного импорта и повторного чтения с отчётом изменений. Позже возможны Wix webhooks с проверкой подписи, дедупликацией и защитой от старых событий плюс периодическая полная сверка. Наличие API key не означает настроенные webhooks: self-hosted app требует своего endpoint; события могут задерживаться и имеют ID для дедупликации. [Product Updated](https://dev.wix.com/docs/api-reference/business-solutions/stores/catalog-v3/products-v3/product-updated).

## Переход к собственному backend

Владелец уточнил последовательность: сначала frontend с Wix, параллельно Hub, затем их соединение через собственный API. Эта последовательность заменяет прежнее предложение сначала завершить импорт каталога в Hub.

**Этап 1 — frontend → Wix и параллельная разработка Hub.** Публичная витрина получает каталог из Wix и использует Wix для корзины, checkout, оплаты и создания заказов. Адаптер витрины отделяет компоненты UI от Wix; серверная часть витрины защищает секреты. API Hub и полный импорт каталога не являются условиями запуска витрины. Параллельно в Hub продолжаются импорт со сверкой существующих товаров, производство, упаковка, fulfilment и подготовка собственных моделей клиентов, каталога и заказов. Текущее чтение Contacts в памяти не заменяет постоянную базу клиентов.

**Этап 2 — frontend → собственный API/backend ← Hub.** Подключить витрину к собственным серверным контрактам по мере готовности функций. Переключать источник истины по областям с проверкой данных и возможностью отката. Подключение каталога к Hub не требует одновременного переноса checkout: собственные правила оплаты, Stripe, refunds, документов и уведомлений должны быть реализованы и проверены отдельно. До этого соответствующие нерабочие controls остаются нерабочими. Не поддерживать два независимых writer без правил конфликтов.

Для публичной витрины нужен отдельный разрешённый набор опубликованных данных и соответствующий API/RLS. Текущие authenticated policies внутренних таблиц не являются контрактом публичного магазина. Приватные документы доставки и производственные чертежи не публикуются вместе с изображениями каталога.

## Публичная витрина: уточнение по предложению владельца

Рабочий архитектурный ориентир — отдельная витрина **Next.js App Router + TypeScript**, отдельный внутренний Angular/PrimeNG Hub и White Corner API с адаптерами Wix/Supabase. Это уточнение плана от 10 сентября 2026, а не уже созданные приложения или выбранный hosting.

| Часть | Ответственность первого этапа |
|---|---|
| Next.js storefront | Публичные страницы и SEO, выбор вариантов, интерфейс корзины |
| Серверный слой/адаптер витрины | Работа с Wix, сессии покупателей и защита секретов; не зависит от готовности API Hub |
| Supabase | Данные Hub и параллельная подготовка собственного backend; не обязательный источник каталога витрины на первом этапе |
| Wix Commerce | Каталог, варианты, корзина, checkout, оплата и создание заказа |
| Angular Hub | Производство, упаковка, fulfilment и внутренняя работа с заказами |

На первом этапе адаптер витрины получает Product/Variant/Category из Wix и преобразует их в модели frontend. Сохранять стабильные внешние ID и не требовать заранее созданный Hub UUID для показа товара. Серверное кеширование позволяет не обращаться к Wix при каждом просмотре. На втором этапе адаптер подключается к собственному API с явным сопоставлением Wix ID и внутренних ID Hub. Каталог и checkout можно переключать независимо.

Wix документирует перенаправление на Wix-hosted checkout. До реализации проверить настройки Headless/OAuth, visitor session и допустимые return URLs именно нашего сайта: действующий административный Orders API key не заменяет сессию покупателя. [Wix Redirects: sample flows](https://dev.wix.com/docs/api-reference/business-management/headless/redirects/sample-flows).

### Рендеринг и обновления

Home, категории, товары и информационные страницы должны отдавать содержательный HTML с корректными metadata, canonical, breadcrumbs и применимыми structured data. Next.js поддерживает предварительно сформированные страницы и управление кешем. Это выбранное удобство реализации; SEO не является исключительной возможностью Next.js, а разделение deployment уменьшает связанность только при правильно разделённых конфигурации и контрактах. [Next.js public pages](https://nextjs.org/docs/app/guides/public-static-pages).

Опции и корзина интерактивны. Фильтры отражаются в URL; до запуска определить индексируемые категории, canonical для фильтров, sitemap и редиректы старых Wix URLs. Поиск и страницы аккаунта рендерить исходя из свежести и сессии; SSR не нужен каждой странице автоматически.

После успешной записи изменений каталога обновлять кеш затронутых товаров и категорий. Webhook является одним из триггеров; повторная сверка покрывает пропущенные события. Обновление Next.js cache не гарантирует очистку независимого CDN: это зависит от hosting и может требовать отдельного purge. [Next.js CDN caching](https://nextjs.org/docs/app/guides/cdn-caching).

### Корзина, безопасность и итоговая цена

Корзина принадлежит visitor session, а не общей серверной учётной записи. В предлагаемой серверной реализации session cookie должна быть HttpOnly, Secure, с выбранной политикой SameSite; state-changing операции требуют защиты от CSRF и проверки принадлежности корзины. Не помещать токены, корзины, аккаунты или ответы с персональными данными в общий кеш.

Браузер передаёт товар, вариант и количество, но не назначает доверенную цену. При добавлении и оформлении Wix проверяет текущие коммерческие данные; расхождение с кешированной карточкой нужно показать покупателю до оплаты. UI цены и наличие в копии каталога не гарантируют возможность покупки.

Секретные ключи Wix, Supabase и Stripe остаются серверными. Запрет на утечку персональных данных не означает, что покупатель не может видеть собственный заказ: такие страницы получают только разрешённые данные после проверки доступа. Подтверждение оплаты берётся из проверенного состояния провайдера, а не из факта возврата браузера на success URL.

### Границы проектов и будущий отказ от Wix

Три логических компонента не требуют немедленно создавать три репозитория или третью независимую серверную систему. В проекте уже есть Supabase Edge Functions. На старте определить, какие контракты реализуются там, а какие — в Next.js server layer, сохраняя один владеющий бизнес-логикой слой. Выбор monorepo/нескольких репозиториев сделать при подготовке витрины. Текущий deployment Hub не менять в рамках документации.

Полный Next.js server runtime, серверные сессии и revalidation требуют подходящего hosting; существующая статическая публикация Hub не заменяет его. Отдельный deployment витрины не изолирует от несовместимых изменений общей БД/API, поэтому нужны совместимые версии контрактов.

После запуска витрины Wix checkout остаётся переходным решением. Supabase — хранилище и серверная платформа, Stripe — платёжный провайдер; их подключение само по себе не реализует commerce backend. Для переключения потребуются собственные правила заказов, скидок, GST, доставки, inventory, платежных состояний, возвратов, документов, идемпотентности и восстановления после ошибок. Adapter сокращает изменения frontend, но не отменяет эту работу.

Приоритет публичного направления — создание frontend с подключением к Wix. Сверка и импорт каталога с сохранением существующих 40 товаров и их связей продолжаются параллельно в направлении Hub и не блокируют витрину. Переключение на собственный API относится ко второму этапу.

## Проверки перед принятием импорта

- Существующие UUID и связи упаковки/чертежей сохранены; повторный импорт не добавляет дубликаты.
- Переименование по тому же Wix ID обновляет товар; два разных ID с одинаковым именем не объединяются.
- Пройдены все страницы товаров и вариантов; отсутствие прав на hidden products явно отражается как неполнота.
- Прерывание и повторная загрузка страницы, Unicode и временные ошибки не теряют ранее сохранённые данные.
- Цветовые варианты и их цены остаются разными, упаковка продолжает использовать согласованное общее правило.
- Исторические заказы, локальные заметки, расчёты, чертежи и выполненные booking не меняются.
- Public frontend не получает приватные поля, ключи или данные клиентов.

## Реализация первого импорта V1

После обновления прав пользователь выполнил production review: **178 Wix products, V1_CATALOG, 30 linked, 148 new, 0 to review**. Сохраняются 10 локальных товаров без Wix ID; все 30 связанных товаров найдены в Wix. Это результат сверки, а не подтверждение импорта.

Миграция `20260910000200_wix_product_catalog.sql` добавляет `wc_wix_catalog_products` (полный снимок карточки с вложенными variants и связь с существующим UUID) и `wc_wix_catalog_jobs` (сохранённый offset, total и run token). Таблицы доступны для чтения только authenticated; запись выполняется через серверные RPC, закрытые для anon/authenticated.

`importCatalog` читает V1 по 25 товаров, включая скрытые товары и варианты. Один SQL-вызов атомарно сохраняет карточки и checkpoint. Новые товары регистрируются по Wix ID, у существующих обновляется название; локальные поля и дочерние связи сохраняются. Кандидат на совпадение с несвязанным локальным названием останавливает порцию. Импорт не удаляет отсутствующие товары и не объединяет разные Wix ID по названию.

В Products → Review Wix catalogue добавлены Import / resume и отдельный подтверждаемый перезапуск. Закрытие вкладки может остановить дальнейшую обработку; уже записанные страницы сохраняются в базе. Повторный запуск продолжает серверный offset. Перезапуск меняет run token и не позволяет старой операции записать страницу в новый запуск. При изменении total или повторе ID между страницами требуется повторная сверка и явный перезапуск.

Снимок сохраняет возвращённые Wix опции, варианты, цены, SKU, описания, media URL, stock и collection IDs без изменения семантики цвета. Это пока не отдельные нормализованные таблицы variants/inventory/categories. Не выполняются отдельное чтение inventory по локациям, перенос самих image files, раскрытие category details или импорт merchant-specific fields. Массив из 1000 вариантов считается потенциально усечённым и останавливает импорт. В карточке Hub добавлен read-only просмотр описания, SKU и вариантов.

Перед публикацией применить и зарегистрировать новую миграцию обычным production-процессом, затем опубликовать Edge Function и Angular. Deployment workflow Edge Function уже отслеживает её каталог; новая миграция не применяется им автоматически. Не запускать полный `db push` с несверенными локальными migrations. После импорта сверить complete/next_offset/expected_total в job, число snapshots текущего run и сохранность существующих ID/дочерних связей. При неизменном исходном каталоге ожидается 178 Wix-снимков и 188 строк реестра вместе с 10 локальными товарами; подтвердить это запросом, не выводить только из UI-счётчика.

Витрина по-прежнему разрабатывается с подключением к Wix независимо от готовности этого импорта.
