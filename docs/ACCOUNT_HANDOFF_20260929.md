# White Corner Hub — передача разработки в другой аккаунт

Снимок: 29 сентября 2026, Australia/Brisbane. Этот документ передаёт контекст проекта и состояние выпуска; следующий запрос владельца определит новую задачу.

## Начать работу

1. Получить доступ к [репозиторию](https://github.com/stasabakumov-sys/whitecorner-orders) в новой учётной записи и открыть актуальный `main`. Прочитать корневой `AGENTS.md` до изменения кода. Для новой работы создать ветку `codex/...` от свежего `main`.
2. Основной интерфейс — `angular-app/` (Angular 21, PrimeNG), сервер — `supabase/functions/`, база — последовательные `supabase/migrations/`. Node: `.nvmrc` (`v22.22.3`), npm: `angular-app/package.json` (`10.9.8`). Проверки Angular: `npm ci`, `npm test -- --watch=false`, `npm run build` из `angular-app/`.
3. Доступ к GitHub и Supabase для нового аккаунта настраивается отдельно. Секреты и service-role key не переносить в чат, документы, клиентский код или Git. Смена аккаунта разработки сама по себе не требует переноса production-проекта, Wix или базы.

## Важная разница между репозиторием и старой рабочей папкой

В общей Windows-папке `C:\Users\stasa\source\whitecorner-orders` локальный `main` остаётся на `93cdf74`, на 47 коммитов позади сохранённого `origin/main` после выпуска. Там находятся десятки **чужих незакоммиченных изменений**, неотслеживаемые исходники, старый черновик `docs/PROJECT_HANDOFF.md` и вложенные worktrees. Эти файлы не попадают в новый clone. Не делать `reset`, `clean`, массовое удаление или перенос всего diff поверх свежего `main`: можно потерять работу или вернуть закрытые уязвимости.

Новый аккаунт должен начать с чистого клона либо отдельного worktree от свежего `origin/main`. Если требуется продолжить именно локальную незавершённую работу, сначала поштучно сверить `git status`, `git worktree list`, `git diff` и неотслеживаемые файлы в старой папке; согласовать, какие изменения действительно нужны. Старый черновик передачи от 28 сентября описывает контекст проекта, но его снимок Git и production устарел.

## Правила продолжения

- Wix остаётся источником импортируемых данных; локальные поля Hub не перезаписываются синхронизацией. Публичный каталог обслуживается отдельной проекцией; таблицы заказов, финансов, почты, production и внутренние файлы требуют активного членства в Hub.
- Сервер проверяет действующую сессию и активное членство; для manager-действий — роль `manager`. Не рассчитывать на скрытые кнопки Angular как на защиту. При изменениях Edge Functions проверить вызывающий Angular service, SQL и deploy workflow.
- Fast Courier booking создаёт реальное отправление и списывает средства. При разработке использовать mocks. Сервер должен всегда проверять review доставки, утверждённую упаковку, выбранный свежий quote, форму, страхование и отдельно подтверждённую сумму. `DELIVERY_REVIEW_ENABLED` не выключает этот booking gate.
- Gmail refresh tokens и API credentials остаются только на сервере. Внутренние Storage buckets остаются private; приложение выдаёт короткоживущие signed URL. Новые миграции делать последовательно, не редактировать применённые SQL-файлы.
- Перед новой production-публикацией проверить реальную схему и текущий `main`. Три catalog migrations (`20260928000100`–`20260928000300`) присутствуют в production, но их исходники не находятся в этом репозитории; hardening сохраняет уже существовавшую публичную проекцию `wc_storefront_catalog`.
